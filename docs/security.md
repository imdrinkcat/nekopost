# 安全配置指南

## 1. 风险说明（请先阅读）

网关会转发**短信验证码、银行通知等高度敏感的内容**。请了解它们会经过哪里：

| 位置 | 是否包含正文 | 保存多久 |
|---|---|---|
| iPhone → 服务器 | 是（HTTPS 加密传输） | — |
| 服务器数据库 | 是 | **仅在投递完成前**（通常不到 1 秒；Telegram 故障时最长 24 小时），之后删除并覆盖 |
| 服务器日志 | **否** | — |
| Telegram 服务器与你的聊天记录 | 是 | 由 Telegram 保存，直到你删除。Bot 聊天**不是**端到端加密的 |
| DeepSeek（仅启用短信过滤时） | 是，**遮盖数字和链接后**的短信；验证码类短信不发送 | 遵循 DeepSeek 的隐私政策，服务器在中国。详见 [sms-filter.md](sms-filter.md#3-隐私) |
| 服务器数据库中被过滤的短信 | 是 | 默认 7 天（`MSGGW_FILTER_KEEP_DAYS`），便于找回误判 |

因此：

- 能登录你 Telegram 账号的人，就能看到转发的验证码。**务必为 Telegram 开启两步验证（Two-Step Verification）**，并定期检查「设备」列表中的活跃会话。
- 不要把 Bot 加入群组或转发 Bot 的消息给他人。
- 只转发确实需要的短信（用快捷指令的关键词 / 发件人条件精确限定），不要「全部转发」。
- 能登录服务器 root 的人，可以在消息投递完成前读到排队中的正文，也能读到 Bot Token。请保护好服务器的 SSH 访问。

## 2. 凭证体系

系统中有三类互相独立的凭证：

| 凭证 | 格式 | 用途 | 存储方式 |
|---|---|---|---|
| 来源凭证 | `mgs_` + 43 字符 | 来源提交消息、查询自己消息的状态 | 数据库只存 SHA-256 哈希 |
| 管理密钥 | `mga_` + 43 字符 | 只读管理 API `/v1/admin/*` | 数据库只存 SHA-256 哈希 |
| Telegram Bot Token | `123456:AA...` | 与 Telegram 通信 | `/etc/msggw/msggw.env`（root 600） |

设计要点：

- **来源隔离**：每个来源有自己的凭证。一个来源的凭证泄露，只影响该来源——执行 `sudo msggw source rotate <id>` 即可让旧凭证立即失效，其他来源不受影响。
- **权限分离**：来源凭证只能提交消息和查询**自己**的消息；无法访问管理接口，无法读取其他来源的任何信息，也无法修改任何配置。管理密钥只能读取状态，不能提交消息。所有写操作（增删来源、改配置）只能在服务器上用命令行完成，或在 Telegram 中由管理员停用 / 启用来源。
- **来源身份不可伪造**：消息的来源由凭证决定。请求体中的 `source` 等字段会被忽略并给出警告。
- 凭证是 256 位随机数，只在创建时显示一次，服务器无法找回原文。
- 被吊销的凭证再被使用时，会记录到对应来源（Bot 中显示「⚠️ 有请求使用了已吊销的凭证」），便于发现泄露。

### 凭证泄露后的处理

| 泄露的内容 | 处理 |
|---|---|
| 某个来源凭证 | `sudo msggw source rotate <id>`，然后更新该设备的配置 |
| 管理密钥 | `sudo msggw admin-key revoke <前缀>` |
| Bot Token | 在 @BotFather 中对该 Bot 执行 `/revoke` 获取新 Token，写入 `msggw.env` 后重启 |

## 3. 网络与接口安全

- **强制 HTTPS**：80 端口只用于证书验证和跳转到 HTTPS；API 只在 443 端口提供。最低 TLS 1.2，并发送 HSTS 头。
- **凭证只放在请求头**（`Authorization: Bearer`），不支持放在 URL 中，避免出现在各类日志里。
- **防暴力破解**：同一 IP 在 10 分钟内认证失败 20 次，将被封禁 15 分钟（HTTP 429）。
- **防滥用**：
  - 每个来源默认每分钟最多 60 条（可配置），一个来源刷屏不影响其他来源；
  - 请求体上限 256 KB，正文上限 12000 字符，标题 256 字符，meta 最多 16 项；
  - 同时处理的请求最多 32 个，超出返回 503；
  - 读取请求头、请求体都有超时，防止慢速连接占用资源。
- **输入处理**：去除控制字符，统一换行；所有内容在发往 Telegram 前做 HTML 转义，客户端无法注入格式或链接预览。
- **不信任客户端元数据**：`occurred_at`（设备时间）仅作参考显示，所有统计和排序使用服务器接收时间；`meta` 只用于显示，不会影响路由、权限或任何系统配置。
- **公开接口最少化**：未认证可访问的只有 `/healthz`，它只返回 `{"status":"ok"}`。
- 服务直接面向公网，不信任 `X-Forwarded-For` 等头。若将来放到反向代理之后，需要相应调整（见 [limitations.md](limitations.md)）。

## 4. Telegram Bot 权限

- 管理员按**数字用户 ID** 识别（用户名、昵称可以随意修改，不可信）。
- 只在私聊中响应；在群组、频道中完全静默。
- 每一次按钮点击都会重新校验管理员身份；按钮数据只接受固定格式的几种动作。
- 会改变状态的操作（停用 / 启用来源）需要二次确认，确认 5 分钟内有效。
- 管理菜单不显示任何消息正文；投递目标的 chat ID 部分隐藏。
- Bot 不具备执行命令、读写文件、操作系统服务的能力。
- 建议在 @BotFather 中设置 `/setjoingroups` → `Disable`。

## 5. 服务器加固

已经默认完成的：

- 服务以无登录 shell 的系统用户 `msggw` 运行，只拥有绑定 80/443 端口的能力。
- systemd 沙箱：根文件系统只读、无法访问 `/home` 和 `/root`、私有 `/tmp`、禁止提权、禁止加载内核模块、限制可用的系统调用。
- 配置文件 `root:root 600`；数据目录 `msggw 700`；数据库文件 `600`。
- 网关**不**需要、也**没有**访问 Docker、systemd 或其他进程的权限；服务器指标只读取 `/proc` 中的公开信息。
- ufw 只放行 22、80、443。

建议你额外做的：

- SSH 只允许密钥登录（`PasswordAuthentication no`），或限制来源 IP。
- 开启系统自动安全更新：`sudo apt install unattended-upgrades`。
- 云服务商控制台开启二次验证。

## 6. 数据保留

| 数据 | 保留 |
|---|---|
| 消息正文、标题、meta | 被短信过滤拦下的消息保留 `MSGGW_FILTER_KEEP_DAYS`（默认 7 天）；其余在投递结束（成功、失败或放弃）后立即删除。数据库开启了 `secure_delete`，被删除的内容会被覆盖；WAL 日志每小时截断一次 |
| 消息元数据（ID、来源、类型、时间、状态、长度） | 默认 30 天（`MSGGW_RETENTION_DAYS`） |
| 内容去重指纹 | 用服务器随机密钥计算的 HMAC，无法反推验证码等短内容；随元数据一起删除 |
| 访问日志 | 只记录方法、路径、状态码、耗时、IP、来源 ID、请求 ID；保留期由 journald 配置决定 |
