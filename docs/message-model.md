# 统一消息模型说明

无论来自哪个来源，服务端都会把提交的内容转换为同一种 `model.Message`，再为每个投递目标生成一条 `model.Delivery`。代码位置：`internal/model/model.go`，校验与规范化在 `internal/httpapi/ingest.go`。

## 字段

| 字段 | 来源 | 说明 |
|---|---|---|
| `id` | 服务端生成 | `m_` + 26 位 Crockford Base32 字符：48 位毫秒时间戳 + 80 位随机数。按时间可排序，例如 `m_01JB7Q4ZK3M8X2N5R6T7V8W9YA` |
| `source` | **凭证决定** | 来源 ID（如 `iphone`）。请求体中的 `source` / `source_id` 会被忽略 |
| `title` | 客户端 | 可选，单行，最多 256 字符 |
| `body` | 客户端 | 可选，多行，最多 `MSGGW_MAX_BODY_CHARS`（默认 12000）字符；`title` 与 `body` 至少一个非空 |
| `type` | 客户端 | 可选，默认 `text`；会转为小写，需匹配 `^[a-z][a-z0-9_.-]{0,31}$` |
| `priority` | 客户端 | `low` / `normal`（默认）/ `high` |
| `occurred_at` | 客户端（**不可信**） | 设备上的事件时间，只用于展示 |
| `meta` | 客户端 | 附加键值，最多 16 项；键为 `^[A-Za-z0-9_.-]{1,32}$`，值最多 256 字符 |
| `idempotency_key` | 客户端 | 可选，最多 128 字符，同一来源内唯一 |
| `received_at` | 服务端 | 服务器接收时间，是统计和排序的依据 |
| `status` | 服务端 | 聚合投递状态，见下文 |
| `content_hash` | 服务端 | HMAC-SHA256(服务器密钥, 来源, 类型, 标题, 正文)，用于无幂等键时的去重。使用密钥是为了防止从哈希反推出验证码等短内容 |
| `dup_count` | 服务端 | 被识别为重复的提交次数 |
| `category` | 服务端 | 短信过滤给出的类别（如 `marketing`），未分类为空，见 [sms-filter.md](sms-filter.md) |

字符长度按 Unicode 字符计算，中文、日文、Emoji 都完整支持。

## 规范化

- 换行：`\r\n` 和 `\r` 统一转为 `\n`。
- 控制字符：会被删除（包括 BOM `U+FEFF`）。`body` 保留 `\n` 和 `\t`；`title`、`meta` 的值和幂等键是单行字段，其中的换行和制表符会被替换为空格。
- 首尾空白：`title` 和 `meta` 的值去掉首尾空白；`body` 去掉末尾的空格、制表符和换行，以及开头的空行，行首缩进保留。
- `meta` 的值：数字和布尔值会转成字符串（`5` → `"5"`，`true` → `"true"`），`null` 会被忽略，空字符串的项会被丢弃。嵌套对象或数组返回 422。
- `occurred_at` 接受以下格式：
  - RFC 3339，例如 `2026-10-25T10:20:00+09:00`。
  - 不带时区的 `2006-01-02T15:04:05`、`2006-01-02 15:04:05`、`2006-01-02 15:04`、`2006/01/02 15:04:05`、`2006/01/02 15:04`，按配置的时区解释。
  - Unix 秒数，或大于 10¹² 时视为毫秒。

  无法解析，或比服务器时间晚 24 小时以上、早 365 天以上的值，会被忽略并给出警告，不会导致请求失败。
- 未知字段：忽略，并在响应的 `warnings` 中列出。

## 可信与不可信

| 可信（服务端决定） | 不可信（客户端声称） |
|---|---|
| 来源身份（由凭证决定） | `occurred_at`：只在 Telegram 中显示为“设备时间”，与接收时间相差超过 2 分钟时才显示 |
| `received_at` | `title`、`body`、`meta`：只作为显示内容，经过 HTML 转义后发送 |
| 消息 ID、状态、统计 | `type`、`priority`：只影响显示标签和是否静默通知 |

附加信息（`meta`）不会参与路由、权限判断或任何系统配置，因此无法用它绕过安全检查。

## 类型标签

已知类型在 Telegram 中会显示中文标签（`internal/render/render.go`）。未知类型会原样显示，所以新增类型不需要修改代码。

| `type` | 显示 |
|---|---|
| `text`（默认） | 不显示标签 |
| `sms` | 💬 短信 |
| `notification` | 🔔 通知 |
| `alert` | 🚨 告警 |
| `event` | 📌 事件 |
| `task` | ✅ 任务 |
| `log` | 📄 日志 |
| `test` | 🧪 测试 |
| 其他，如 `ci.build` | `ci.build` |

## 优先级

| 值 | 效果 |
|---|---|
| `low` | 静默投递（Telegram `disable_notification`，手机不响铃） |
| `normal` | 正常通知 |
| `high` | 消息开头加 `❗` |

优先级目前不影响投递顺序，所有消息按到期时间依次处理。

## 状态

消息状态（`status`）是该消息所有投递记录的聚合结果：

| 值 | 中文（`status_text`） | 是否终态 |
|---|---|---|
| `queued` | 已接收，等待投递 | 否 |
| `sending` | 正在投递 | 否 |
| `retrying` | 投递暂未成功，正在重试 | 否 |
| `delivered` | 已送达 Telegram | 是 |
| `partial` | 部分目标已送达 | 是 |
| `failed` | 投递失败 | 是 |
| `uncertain` | 投递结果不确定 | 是 |
| `not_routed` | 无投递目标（未转发） | 是 |
| `classifying` | 已接收，正在识别是否为广告 | 否（仅启用[短信过滤](sms-filter.md)时） |
| `filtered` | 已过滤（不需要推送的短信），未转发 | 是（可在 Bot 中找回，找回后回到 `queued`） |

“服务器已接收”和“Telegram 已收到”是两个不同的阶段：只有 `delivered` 表示 Telegram 确认收到了消息。`uncertain` 表示至少有一次尝试结果未知，服务端已经放弃重试，Telegram 可能收到了，也可能没收到。

单个投递记录的状态（`deliveries[].state`）：`pending`、`sending`、`retrying`、`delivered`、`failed`、`uncertain`，启用短信过滤时还有 `held`（等待分类）和 `filtered`。状态转换见 [architecture.md](architecture.md#4-投递语义与状态机)。

## 数据保留

| 数据 | 保留时长 |
|---|---|
| 标题、正文、meta（`payloads` 表） | 只保留到消息进入终态，之后立即删除（磁盘页会被覆盖，WAL 每小时截断）。被短信过滤拦下的消息例外：保留 `MSGGW_FILTER_KEEP_DAYS`（默认 7 天）以便找回 |
| 元数据（`messages`、`deliveries` 表，不含正文） | `MSGGW_RETENTION_DAYS`（默认 30 天） |
| 幂等键 | 随元数据一起保留，保留期内有效 |

日志中从不记录正文、凭证和查询字符串。

## 在 Telegram 中的呈现

消息正文里只有内容，锁屏通知和聊天中都只显示内容。来源、类型和分类是消息下方并排的两个按钮。不单独显示时间，因为 Telegram 本身会显示消息的到达时间：

```
❗ 招商银行                        ← 标题（加粗，仅第一段）；优先级 high 才有 ❗
验证码 123456，5 分钟内有效。      ← 正文

phone: 主卡                        ← meta（按键名排序，仅最后一段）

[📱 iPhone] [💬 短信 · 验证码 (1/2)]   ← 按钮：来源 | 类型 · 分类（启用短信过滤时）；分段时才有 (i/n)
```

- 点击任一按钮会弹出这条消息的详情：来源、类型与分类、接收时间、设备时间、投递状态、消息 ID。消息本身不会被修改。只有管理员能看到详情；消息元数据超过保留期（默认 30 天）后，会提示记录已过期。
- 类型为 `text` 且没有分类时，只有来源一个按钮。
- 分段消息的每一段都带按钮。
- 类型为 `text` 且没有分类时，只有来源一个按钮。
- 来源名称和图标在服务器上用 `msggw source set` 配置，没有设置图标时默认为 📨。
- 使用 HTML 格式发送，所有用户内容都会转义。如果 Telegram 报告格式解析错误，会自动改用纯文本重发。
- 链接预览一律关闭。
- **拆分**：Telegram 单条消息最多 4096 个 UTF-16 单位（一个 Emoji 通常占 2 个）。超长时正文按长度切分，在每段最后 25% 的范围内优先在换行处断开，其次在空格或 `。！？.!?` 处断开，不会切断单个字符。每段都带有 `(i/n)` 标记。分段投递可以从中断处续传，见架构文档。
